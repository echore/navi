<div class="lang-zh">
<blockquote>
</blockquote>
<pre><code>大多数复盘失败不是因为没有做，而是因为做完了什么都没变。这篇笔记的目的是定下一个标准：复盘问什么、怎么做、怎么让它真正积累到下一次。
</code></pre>
<hr>
<h2>为什么大多数复盘没用</h2>
<p>三个常见失败原因：</p>
<p><strong>1. 只说&quot;做得好&quot;和&quot;做得不好&quot;，没有追问原因</strong><br>&quot;测试没做到位&quot;是现象，不是原因。原因是&quot;每步完成时没有强制要求汇报测试结果&quot;。只找现象，下次还会重蹈。</p>
<p><strong>2. 洞察停留在脑子里，没有落进系统</strong><br>复盘出来的东西，如果只是&quot;我以后要注意&quot;，基本等于没用。人脑不可靠，系统才可靠。洞察必须变成文档、规则、或者流程的改动。</p>
<p><strong>3. 没有后续检验机制</strong><br>这次复盘出来的改进，下次有没有真的做到？没有人检验，改进就是一句空话。</p>
<hr>
<h2>复盘的两个层次</h2>
<h3>层次一：这件事本身（项目复盘）</h3>
<p>这次做了什么、哪里出问题、下次怎么改。</p>
<h3>层次二：我们怎么合作（协作复盘）</h3>
<p>AI 和我之间的配合哪里顺、哪里卡、规则是否需要更新。</p>
<p>两个层次都要做，缺一个都是不完整的。</p>
<hr>
<h2>标准复盘问题清单</h2>
<h3>项目层面</h3>
<p><strong>关于结果</strong></p>
<ul>
<li><p>我们设定的目标是什么？最终做到了吗？</p>
</li>
<li><p>哪些做到了预期，哪些没有？</p>
</li>
</ul>
<p><strong>关于过程</strong></p>
<ul>
<li><p>哪个环节卡住了？为什么？（追问到根本原因，不停在现象）</p>
</li>
<li><p>有没有哪步做了很多次才对？原因是什么？</p>
</li>
<li><p>有没有本可以更简单的做法，但我们绕了弯路？</p>
</li>
</ul>
<p><strong>关于决策</strong></p>
<ul>
<li><p>哪个决策现在看来是对的？为什么？</p>
</li>
<li><p>哪个决策现在看来是错的？当时为什么做了这个决定？</p>
</li>
</ul>
<hr>
<h3>协作层面</h3>
<p><strong>关于启动</strong></p>
<ul>
<li><p>开始前，需求有没有说清楚？AI 有没有真正理解我要什么？</p>
</li>
<li><p>计划有没有写出来？计划够不够细？</p>
</li>
</ul>
<p><strong>关于执行</strong></p>
<ul>
<li><p>AI 有没有每步都汇报测试结果？还是只说&quot;完成了&quot;？</p>
</li>
<li><p>有没有遇到 AI 给出方案但我无法判断对不对的情况？</p>
</li>
<li><p>有没有遇到来回修改同一个问题超过两次的情况？（超过两次说明根因没找到）</p>
</li>
</ul>
<p><strong>关于规则</strong></p>
<ul>
<li><p>SOP 里有没有哪条规则这次没遵守？为什么？</p>
</li>
<li><p>有没有遇到 SOP 没有覆盖到的情况？需要新增规则吗？</p>
</li>
<li><p>有没有哪条规则这次证明是有效的，应该强化？</p>
</li>
</ul>
<hr>
<h2>复盘产出必须是这三样之一</h2>
<p>复盘结束，洞察必须落地成：</p>
<p><strong>1. 更新 SOP</strong><br>如果发现了一个可以避免的问题，就把对应的规则加进 SOP。这是最重要的产出。</p>
<p><strong>2. 更新 CLAUDE.md</strong><br>如果是这个项目特有的改进，更新项目的 CLAUDE.md，下次 Session 自动生效。</p>
<p><strong>3. 写进复盘笔记</strong><br>如果是一个更大的认知或模式，写进笔记，加入知识网络。</p>
<p><strong>没有这三样产出之一的复盘，等于没有复盘。</strong></p>
<hr>
<h2>怎么让复盘真正积累</h2>
<h3>短期：每次 Session 结束做小复盘</h3>
<p>不需要很长，三个问题就够：</p>
<ol>
<li><p>这次哪里做得好，值得保留？</p>
</li>
<li><p>哪里卡住了，下次怎么避免？</p>
</li>
<li><p>有没有需要更新 SOP 或 CLAUDE.md 的地方？</p>
</li>
</ol>
<p>写进 Session 交接里，存入 Build Log。</p>
<h3>中期：每个项目结束做完整复盘</h3>
<p>用上面的完整问题清单过一遍，重点看：</p>
<ul>
<li><p>这个项目里反复出现的问题是什么？</p>
</li>
<li><p>有没有值得写进通用 SOP 的新规则？</p>
</li>
</ul>
<h3>长期：定期回顾 SOP</h3>
<p>每隔一两个月，重新读一遍 SOP：</p>
<ul>
<li><p>哪些规则真的在用？</p>
</li>
<li><p>哪些规则从来没执行过？（说明要么不实用，要么需要强化执行机制）</p>
</li>
<li><p>有没有新的经验需要加进来？</p>
</li>
</ul>
<hr>
<h2>复盘的核心原则</h2>
<p><strong>原则一：追问原因，不停在现象</strong><br>每个问题问完，再问一次&quot;为什么&quot;。直到找到可以改变的根因为止。</p>
<p><strong>原则二：洞察必须进系统，不能只在脑子里</strong><br>想到了但没写下来，等于没想到。</p>
<p><strong>原则三：改进必须具体，不能是&quot;以后要注意&quot;</strong><br>&quot;以后要注意测试&quot;没用。&quot;每步完成时，我会说：给我看测试命令和输出结果&quot;——这才有用。</p>
<p><strong>原则四：不要在状态差的时候做复盘</strong><br>复盘需要清醒的头脑和相对客观的视角。情绪低落时看什么都是问题，那时候的复盘结论不可靠。</p>
<p><strong>原则五：复盘的目的不是自我批评，是提取模式</strong><br>不是&quot;我哪里做错了&quot;，而是&quot;这件事有没有可以学到的规律&quot;。前者消耗能量，后者积累能量。</p>
<hr>
<h2>这次复盘的样本</h2>
<p>今天我们复盘了 Navi Site 项目的协作过程，产出了：</p>
<p><strong>发现的问题</strong>：</p>
<ul>
<li><p>进度不可见（没有实时清单）</p>
</li>
<li><p>测试执行不彻底（没强制要求汇报结果）</p>
</li>
<li><p>Session 断档（交接不够细）</p>
</li>
<li><p>来回修改太多（没有先追问原因）</p>
</li>
</ul>
<p><strong>落地的产出</strong>：</p>
<ul>
<li><p>更新了 SOP（加了 11 条规则，含 Bug 修复顺序、对齐设计概念等）</p>
</li>
<li><p>建了 CLAUDE.md（规则自动在每次 Session 生效）</p>
</li>
<li><p>写了工作流笔记（方法论本身可以复用）</p>
</li>
</ul>
<p><strong>还不完美的地方</strong>：</p>
<ul>
<li>复盘本身也经历了多次来回，说明&quot;怎么复盘&quot;本身还需要标准——这篇笔记就是为了解决这个问题。</li>
</ul>
<hr>
<h2>从复盘到 SOP：什么值得写进去</h2>
<p>复盘结束后，不是所有经验都该进 SOP。进 SOP 的标准是三条，缺一不可：</p>
<p><strong>1. 重复性</strong> — 这个问题会不会在下个项目里再出现？<br>只出现一次的特殊情况不值得进 SOP，写进项目笔记就好。</p>
<p><strong>2. 可预防性</strong> — 这个问题能不能靠一条规则提前避免？<br>如果是外部原因（比如 API 突然挂了）无法预防，就不用写。</p>
<p><strong>3. 可验证性</strong> — 这条规则有没有执行，能不能检验？<br>&quot;以后要注意沟通&quot;无法验证，不算规则。&quot;每步完成后说出测试命令和结果&quot;可以验证，是规则。</p>
<p><strong>三条都满足 → 进 SOP。只满足部分 → 写进复盘笔记留存。</strong></p>
<p>写进 SOP 的格式要求：</p>
<ul>
<li><p>说清楚<strong>做什么</strong>，不说&quot;要注意 X&quot;</p>
</li>
<li><p>说清楚<strong>什么时候做</strong>，触发条件要明确</p>
</li>
<li><p>说清楚<strong>怎么验证</strong>，执行了没有能被检查</p>
</li>
</ul>
<hr>
<h2>让系统自我延续：三个必须有的环节</h2>
<p>SOP 写好了不代表它会被用。系统要能自我延续，需要三个环节都在：</p>
<p><strong>入口：新项目怎么启动系统</strong></p>
<p>每次开新项目，有没有一个固定的触发动作？</p>
<p>通用标准：</p>
<ul>
<li><p>读 SOP，确认这个项目适用哪些规则</p>
</li>
<li><p>建项目专属的 CLAUDE.md，把适用规则和项目信息写进去</p>
</li>
<li><p>建 Obsidian 项目笔记，创建阶段清单和专属 DoD</p>
</li>
</ul>
<p>没有固定入口，系统就是摆设——每次都要重新想&quot;我应该做什么&quot;。</p>
<p><strong>容器：规则和进度存在哪里</strong></p>
<p>运行中，AI 怎么随时知道规则是什么？</p>
<p>通用标准：</p>
<ul>
<li><p>CLAUDE.md 放在项目根目录，Claude Code 自动读取</p>
</li>
<li><p>Obsidian Build Log 记录每次 Session 进度和交接</p>
</li>
<li><p>两个地方分工明确：CLAUDE.md 存规则，Build Log 存进度</p>
</li>
</ul>
<p><strong>出口：项目结束怎么写回系统</strong></p>
<p>结束时，有没有一个固定动作把新经验写回去？</p>
<p>通用标准：</p>
<ul>
<li><p>做完整复盘，用本笔记的问题清单过一遍</p>
</li>
<li><p>符合三条标准的经验 → 更新通用 SOP</p>
</li>
<li><p>项目特有的经验 → 写进项目复盘笔记</p>
</li>
<li><p>Session 结束 → 写交接，存 Build Log</p>
</li>
</ul>
<p><strong>三个环节缺任何一个，系统就会断。</strong></p>
<pre><code class="language-plain">新项目开始
    ↓
入口：读 SOP → 建 CLAUDE.md → 建项目笔记
    ↓
容器：CLAUDE.md（规则）+ Build Log（进度）
    ↓
出口：复盘 → 更新 SOP → 写交接
    ↓
下个项目站在更高起点上开始
</code></pre>
